# 有缺陷的互斥示例

## 核心代码

三个任务共用 `LcdPrintTask`，通过不同参数在 LCD 不同行显示，但访问的是同一个 LCD 和 I²C 通道。单核任务交替执行，也可能让未完成的硬件操作交错；不一定要阻塞，同优先级时间片轮转也会切换任务。

实际源码节选（省略显示细节）：

```c
static int g_LCDCanUse = 1;

if (g_LCDCanUse)       // ① 判断空闲
{
    g_LCDCanUse = 0;   // ② 占用
    // LCD 显示操作
    g_LCDCanUse = 1;   // ③ 释放
}
```

## 易混淆结论

- **全局变量共享，不代表重新判断**：A 通过 `if` 后被切走，B 将标志置零；A 恢复时继续执行后面的置零和显示，不会回头重新执行 `if`。
- **漏洞在判断与置零之间**：A 判断成功但还没置零，B 也能判断成功；若 A 已置零且尚未释放，B 就无法进入。
- **判断和占用必须不可分割**：不能让其他任务插入两步之间，分别执行两句 C 代码不能保证原子性。
- **自减也不保证原子性**：普通变量的 `--` 可拆成读内存、寄存器减一、写回内存。A 读到 1 后被切走，B 减成 0；A 恢复时寄存器仍是先前保存的 1，也会写回 0，两个任务都可能通过 `== 0` 判断。
- **只保护判断与占用**：课程用关中断说明如何避免这段过程被任务切换打断。标志置零后即可恢复中断，不必一直关闭到 LCD 操作完成；其他任务看到 0 就无法进入。实际工程应使用适合 FreeRTOS 的临界区或互斥机制。
- **互斥正确不等于等待高效**：获取失败后循环重试属于忙等，仍占 CPU；若等待者优先级更高且始终就绪，持有 LCD 的低优先级任务无法运行，也无法释放资源。
- **阻塞任务不参与就绪任务竞争**：获取失败后阻塞，持有者才能继续运行；释放资源后再唤醒等待者。未超时、未解除阻塞时，Tick 到来也不会仅因其优先级高就调度它。

自减、关中断与阻塞等待是本节后续分析思路，06 工程当前仍使用上面的全局标志，尚未实现这些改进。
