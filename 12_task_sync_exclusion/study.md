# 有缺陷的同步示例

## 核心代码

同步是任务之间的先后依赖：`CalcTask` 计算完成，`LcdPrintTask` 再显示结果。

实际源码节选（省略计时和显示）：

```c
static volatile int g_calc_end = 0;

// CalcTask
for (i = 0; i < 10000000; i++)
    g_sum += i;
g_calc_end = 1;

// LcdPrintTask
vTaskDelay(3000);
while (g_calc_end == 0);
```

## 易混淆结论

- **延时不等于完成**：`vTaskDelay(3000)` 只等待 3000 tick，不能保证计算完成。本工程 tick 为 1 ms，约为 3 秒。
- **忙等不等于阻塞**：`while (g_calc_end == 0);` 循环体为空，仍持续检查标志、占用 CPU，任务没有进入阻塞态。
- **同优先级忙等**：显示任务参与时间片轮转，挤占计算任务的运行时间；课程中先让显示任务阻塞，计算耗时约减半。
- **高优先级忙等**：若显示任务优先级更高且不阻塞，计算任务得不到运行机会，无法修改标志，等待无法结束。
- **volatile 的作用**：每次检查实际读取变量，避免编译器一直复用旧值；不让出 CPU，不使任务阻塞，也不提供互斥或原子性。
- **合理的同步**：等待任务进入阻塞态；计算任务准备好结果后发出通知，再唤醒等待任务。
- **唤醒与抢占**：被唤醒的任务先进入就绪态；在本工程的抢占式调度下，若它优先级高于当前任务，就会抢占。

`vTaskDelay(3000)` 是用于对比忙等开销的实验，不是可靠的“计算完成”通知机制。

# 第31集：环形缓冲区

本节为独立知识点，无对应工程，附记于12工程。

## 读写下标与空满判断

- `r` 指向下一次读取位置，`w` 指向下一次写入位置；数组从0开始编号。
- 写入后推进 `w`，读出后推进 `r`；到末尾后回到0，数组本身不移动。
- 读出后不必清零，推进 `r` 就表示该数据已被取走。

```c
// 长度为N，预留一个空位的方案
// 空：r == w
// 满：(w + 1) % N == r

// 确认未满后写入
buffer[w] = data;
w = (w + 1) % N;

// 确认非空后读取
data = buffer[r];
r = (r + 1) % N;
```

- 8格最多存7个数据；空位随下标移动，不是固定废弃某一格。
- 初始 `r = w = 0`，写入10、20、30再读两次：`w = 3，r = 2`，下次读30。
- `r = 3，w = 2` 时已满，有效数据顺序为 `3→4→5→6→7→0→1`。再写位置2不会立即覆盖未读数据，但会使下标相等，把满误判为空；无需判断“第几轮”。

## 为什么不用共享计数变量

- 写任务执行 `number++`、读任务执行 `number--`，双方都修改同一变量。
- `++/--` 包含读取、计算、写回，中间可能切换任务。
- 初值5：写任务读到5后被切走，读任务减为4；写任务恢复后仍按旧值写回6。实际数量应为5，减1的结果丢失。

## 使用条件与局限

- 本节方案限定一个写入方、一个读取方：写入方修改 `w`，读取方修改 `r`，双方读取对方下标判断空满。该分工避免共同修改计数值的冲突，不代表任意平台都无需考虑原子访问和内存顺序。
- 两个写入方若都拿到 `w = 2`，B写完并推进到3后，A仍使用旧下标2，会覆盖B的数据。
- 环形缓冲区本身不提供阻塞和唤醒。高优先级读任务在空缓冲区上忙等，会使低优先级写任务无法运行。
- FreeRTOS队列进一步提供并发访问保护，以及等待数据或空间时的阻塞与唤醒机制。

# 第32集：队列的本质

本节以概念和运行机制为主，无新增实操工程，附记于12工程。

## 存储与保护

- 队列在环形缓冲区基础上增加并发保护、阻塞与唤醒机制；使用流程是创建、发送、接收。
- 读写位置决定数据存取位置，数据个数判断空满，两者都需要。
- 计数更新等关键操作受到保护，避免多个任务交错修改造成结果丢失；容量8可以存8个数据，不必预留一格。

## 等待与返回值

```c
// 示意：queue已创建，data类型与队列元素类型一致
if (xQueueReceive(queue, &data, 100) == pdPASS) {
    // 接收成功，才处理data
}
// 发送也可以等待空位
ret = xQueueSend(queue, &data, 100);
```

- `100` 是最多阻塞等待100个tick，不是固定延时，也不保证函数恰好在第100个tick返回；恢复执行仍需获得CPU。
- 读队列：有数据立即取出；为空且允许等待则阻塞。写队列：有空间立即写入；已满且允许等待则阻塞。等待参数为0时不阻塞。
- 第20个tick任务A写入数据，可以提前唤醒等待接收的B；是任务写入触发唤醒，不是tick写数据。
- 一直没有数据或空间时，可因超时解除等待；必须检查函数返回值，不能把唤醒当成操作成功。

## 等待链表与任务状态

- 队列有发送等待链表和接收等待链表，分别记录等空位、等数据的任务；调用方不需要知道等待任务的句柄。
- 有限时间等待的普通场景：任务从就绪链表移除，同时进入对应队列等待链表和延时链表。
- 数据或空间到来、等待超时，均需解除本次等待，清理两处记录，再恢复就绪；不能留下旧的超时记录。
- **唤醒只是恢复就绪，不等于立即运行**。是否抢占取决于优先级与调度方式；本工程采用抢占式调度，高优先级任务恢复就绪可抢占当前任务。
- 队列满时，高优先级发送任务A阻塞，低优先级接收任务B才能运行；B取走数据后唤醒A，A获得CPU继续尝试发送。

## 阻塞与忙等

- 队列阻塞等待期间不占用CPU；超时返回后再次等待，也不同于持续循环检查。
- `while (队列为空);` 是忙等，任务仍参与调度，可能让低优先级写任务一直无法运行。
- 忙等并非绝对不能切走：高优先级任务可以抢占，同优先级任务可能按时间片轮转；它只是没有主动进入阻塞态。
