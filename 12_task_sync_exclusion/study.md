# 有缺陷的同步示例

## 核心代码

同步是任务之间的先后依赖：`CalcTask` 计算完成，`LcdPrintTask` 再显示结果。

实际源码节选（省略计时和显示）：

```c
static volatile int g_calc_end = 0;

// CalcTask
for (i = 0; i < 10000000; i++)
    g_sum += i;
g_calc_end = 1;

// LcdPrintTask
vTaskDelay(3000);
while (g_calc_end == 0);
```

## 易混淆结论

- **延时不等于完成**：`vTaskDelay(3000)` 只等待 3000 tick，不能保证计算完成。本工程 tick 为 1 ms，约为 3 秒。
- **忙等不等于阻塞**：`while (g_calc_end == 0);` 循环体为空，仍持续检查标志、占用 CPU，任务没有进入阻塞态。
- **同优先级忙等**：显示任务参与时间片轮转，挤占计算任务的运行时间；课程中先让显示任务阻塞，计算耗时约减半。
- **高优先级忙等**：若显示任务优先级更高且不阻塞，计算任务得不到运行机会，无法修改标志，等待无法结束。
- **volatile 的作用**：每次检查实际读取变量，避免编译器一直复用旧值；不让出 CPU，不使任务阻塞，也不提供互斥或原子性。
- **合理的同步**：等待任务进入阻塞态；计算任务准备好结果后发出通知，再唤醒等待任务。
- **唤醒与抢占**：被唤醒的任务先进入就绪态；在本工程的抢占式调度下，若它优先级高于当前任务，就会抢占。

`vTaskDelay(3000)` 是用于对比忙等开销的实验，不是可靠的“计算完成”通知机制。

# 第31集：环形缓冲区

本节为独立知识点，无对应工程，附记于12工程。

## 读写下标与空满判断

- `r` 指向下一次读取位置，`w` 指向下一次写入位置；数组从0开始编号。
- 写入后推进 `w`，读出后推进 `r`；到末尾后回到0，数组本身不移动。
- 读出后不必清零，推进 `r` 就表示该数据已被取走。

```c
// 长度为N，预留一个空位的方案
// 空：r == w
// 满：(w + 1) % N == r

// 确认未满后写入
buffer[w] = data;
w = (w + 1) % N;

// 确认非空后读取
data = buffer[r];
r = (r + 1) % N;
```

- 8格最多存7个数据；空位随下标移动，不是固定废弃某一格。
- 初始 `r = w = 0`，写入10、20、30再读两次：`w = 3，r = 2`，下次读30。
- `r = 3，w = 2` 时已满，有效数据顺序为 `3→4→5→6→7→0→1`。再写位置2不会立即覆盖未读数据，但会使下标相等，把满误判为空；无需判断“第几轮”。

## 为什么不用共享计数变量

- 写任务执行 `number++`、读任务执行 `number--`，双方都修改同一变量。
- `++/--` 包含读取、计算、写回，中间可能切换任务。
- 初值5：写任务读到5后被切走，读任务减为4；写任务恢复后仍按旧值写回6。实际数量应为5，减1的结果丢失。

## 使用条件与局限

- 本节方案限定一个写入方、一个读取方：写入方修改 `w`，读取方修改 `r`，双方读取对方下标判断空满。该分工避免共同修改计数值的冲突，不代表任意平台都无需考虑原子访问和内存顺序。
- 两个写入方若都拿到 `w = 2`，B写完并推进到3后，A仍使用旧下标2，会覆盖B的数据。
- 环形缓冲区本身不提供阻塞和唤醒。高优先级读任务在空缓冲区上忙等，会使低优先级写任务无法运行。
- FreeRTOS队列进一步提供并发访问保护，以及等待数据或空间时的阻塞与唤醒机制。
