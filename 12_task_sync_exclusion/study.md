# 有缺陷的同步示例

## 核心代码

同步是任务之间的先后依赖：`CalcTask` 计算完成，`LcdPrintTask` 再显示结果。

实际源码节选（省略计时和显示）：

```c
static volatile int g_calc_end = 0;

// CalcTask
for (i = 0; i < 10000000; i++)
    g_sum += i;
g_calc_end = 1;

// LcdPrintTask
vTaskDelay(3000);
while (g_calc_end == 0);
```

## 易混淆结论

- **延时不等于完成**：`vTaskDelay(3000)` 只等待 3000 tick，不能保证计算完成。本工程 tick 为 1 ms，约为 3 秒。
- **忙等不等于阻塞**：`while (g_calc_end == 0);` 循环体为空，仍持续检查标志、占用 CPU，任务没有进入阻塞态。
- **同优先级忙等**：显示任务参与时间片轮转，挤占计算任务的运行时间；课程中先让显示任务阻塞，计算耗时约减半。
- **高优先级忙等**：若显示任务优先级更高且不阻塞，计算任务得不到运行机会，无法修改标志，等待无法结束。
- **volatile 的作用**：每次检查实际读取变量，避免编译器一直复用旧值；不让出 CPU，不使任务阻塞，也不提供互斥或原子性。
- **合理的同步**：等待任务进入阻塞态；计算任务准备好结果后发出通知，再唤醒等待任务。
- **唤醒与抢占**：被唤醒的任务先进入就绪态；在本工程的抢占式调度下，若它优先级高于当前任务，就会抢占。

`vTaskDelay(3000)` 是用于对比忙等开销的实验，不是可靠的“计算完成”通知机制。
