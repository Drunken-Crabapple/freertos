# 空闲任务

## 任务函数不能直接返回

- 任务入口函数可以执行有限次数，但结束前必须删除自己，不能直接返回。
- 创建任务不是普通函数调用，任务结束不会返回到 `main()` 中创建任务的下一行。
- `pxPortInitialiseStack()` 在任务栈中设置初始现场：PC 对应任务入口，LR 对应 `prvTaskExitError()`。
- 任务入口函数直接返回，会进入 `prvTaskExitError()`。当前工程启用了断言，会屏蔽调度相关中断并停在死循环中，正常调度无法继续。
- 这里不是屏蔽所有硬件中断，而是屏蔽包含调度中断在内的一定优先级范围的中断。

## 空循环与删除任务

```c
while (1) {}              // 任务仍然存在，一直就绪，不主动让出 CPU
vTaskDelete(NULL);        // 当前任务删除自己
vTaskDelete(xTaskHandle); // 删除句柄指定的任务
```

- 普通空循环仍可被更高优先级任务抢占；进入上述错误处理后，正常任务抢占无法继续。
- 高优先级任务一直就绪，会使低优先级任务无法运行；空循环不是“偶尔占用一下 CPU”。
- 自删任务退出调度，不会继续执行 `vTaskDelete(NULL)` 后面的代码。

## 延时到期只代表就绪

```c
Led_Control(LED_GREEN, 1);
vTaskDelay(500);
Led_Control(LED_GREEN, 0);
```

- `vTaskDelay()` 使当前任务进入阻塞态；延时到期只使任务恢复就绪，不保证立即运行。
- 任务再次获得 CPU 后，才执行后面的关灯代码。延时期间 GPIO 保持输出状态，不需要任务一直运行。
- 若更高优先级任务一直就绪，LED 任务即使延时到期也无法关灯，亮灯时间会延长。
- 等待 CPU 不会重新开始这次延时：任务已就绪，获得 CPU 后继续执行。
- 当前工程 tick 频率为 1000 Hz，500 tick 对应 500 ms；相对延时受 tick 相位影响，实际恢复执行还受调度影响，不是精确定时关灯。
- `mdelay()` 忙等，任务仍然就绪；`vTaskDelay()` 阻塞，当前任务暂时不参与调度。

## 空闲任务与资源回收

- 调度器启动时创建空闲任务，其优先级为 0。
- 空闲任务不主动阻塞，其他任务都阻塞时仍有任务可运行；更高优先级任务就绪后可抢占它。
- 只要还有优先级大于 0 的任务就绪，空闲任务就无法运行。仅让其中一个任务阻塞并不足够。
- 动态任务删除自己时还在使用自己的栈，资源回收交给空闲任务完成。

```text
任务删除自己 → 退出正常调度，进入等待清理链表
            → 空闲任务获得 CPU → 清理任务资源
```

- 空闲任务调用 `prvCheckTasksWaitingTermination()`，从 `xTasksWaitingTermination` 取得待清理任务的 TCB，移除其链表节点，再调用 `prvDeleteTCB(pxTCB)`。
- 执行清理的是空闲任务；`pxTCB` 指向被删除的任务，释放的是被删除任务的动态栈和 TCB。
- 退出调度不等于内存已释放。不断创建、自删动态任务，而空闲任务无法运行，会导致待回收内存积累，最终可能内存不足。
- 当前 LED 任务由 `xTaskCreateStatic()` 创建，静态栈和静态 TCB 不会作为动态内存释放。

## 空闲任务钩子

- `vApplicationIdleHook()` 在空闲任务内部调用，不是独立任务，可用于简单统计，不能执行阻塞操作。
- `configUSE_IDLE_HOOK` 为 1 时启用；当前工程为 0，未启用。
- 空闲任务没有运行机会，钩子也不会执行，钩子中的计数器不会增加。
