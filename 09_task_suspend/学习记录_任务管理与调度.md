# FreeRTOS 学习记录：任务管理与调度

日期：2026-09-13  
对应工程：09_task_suspend  
对应课程：[韦东山 FreeRTOS 第 24 P：任务管理与调度](https://www.bilibili.com/video/BV1Jw411i7Fz/?p=24)

## 一、本节核心要点（按视频顺序）

1. **先选最高的就绪优先级，再在该优先级内轮转。**高优先级任务持续就绪，低优先级任务就得不到 CPU。高优先级任务阻塞或挂起后，低优先级任务才有机会运行。
2. **每个优先级有一条就绪链表。**`pxReadyTasksLists[N]` 管理优先级 N 的就绪任务。视频配置有 56 个优先级，范围是 0～55。
3. **运行中的任务仍在就绪链表里。**同级轮转不摘除节点、不改变节点的前后连接，只推进链表游标，再选出任务。
4. **Tick 推进计时，也能触发时间片轮转。**在开启抢占和时间片轮转时，同一最高就绪优先级的多个任务可在 Tick 驱动下轮转。视频中 Tick 为 1 ms，但任务每次获得 CPU 不保证能运行满 1 ms。
5. **创建或恢复高优先级任务，可以在两个 Tick 之间触发抢占。**不必等下一个 Tick，也不必等当前任务主动延时。
6. **延时、挂起和恢复通过状态节点迁移体现。**延时到期由 Tick 处理逻辑解除阻塞；显式挂起需要恢复操作解除。

以上调度讨论以本课程的单核、抢占式调度为前提；临界区等情况可能推迟实际切换。

| 操作 | 状态节点的变化 |
|---|---|
| 创建成功 | 加入对应优先级的就绪链表 |
| `vTaskDelay(2)` | 就绪链表 → 延时链表，唤醒时刻为当前 Tick + 2（暂不考虑溢出） |
| 延时到期 | 延时链表 → 对应优先级的就绪链表 |
| `vTaskSuspend(handle)` | 原状态链表 → 挂起链表 |
| `vTaskResume(handle)` | 挂起链表 → 对应当前优先级的就绪链表 |

## 二、这几天反复问过、容易混淆的地方

### 1. 节点、TCB 和几个指针分别是什么？

| 成员或变量 | 含义 |
|---|---|
| `xStateListItem` | TCB 内嵌的状态链表节点 |
| `pvOwner` | 节点对应的任务 TCB 地址；换链表时仍指向同一个 TCB |
| `pvContainer` | 节点当前所属链表的地址；移除后置空 |
| `pxNext`、`pxPrevious` | 节点的后继、前驱连接 |
| `pxIndex` | 每条链表自己的遍历游标，不等同于正在运行的任务 |
| `pxCurrentTCB` | 当前运行或切换过程中选中的任务 TCB 指针 |
| `xListEnd` | 链表哨兵，不对应任务，遍历选任务时要跳过 |

节点从就绪链表移到挂起链表，没有新建节点，也没有搬移 TCB 或任务栈。仅修改 `pvContainer` 不够：还必须维护邻居指针、节点数量以及必要的游标调整。

### 2. 为什么移除节点时，游标要退到前一个节点？

只有 `pxIndex` 恰好指向被移除节点时才调整它。下一次选任务会“先前进一步，再取节点”，所以先退到前一个节点，下一次才能接着访问原来的后继。若直接放到后继，下次再前进就会跳过它。

正常轮转则只读取连接：

```c
pxList->pxIndex = pxList->pxIndex->pxNext;
/* 若遇到哨兵，再前进一步 */
pxCurrentTCB = pxList->pxIndex->pvOwner;
```

这里改变的是游标和选中的 TCB，节点的 `pxNext`、`pxPrevious` 不变。

### 3. 恢复后要等原来的延时结束吗？

不用。例：Tick 100 调用 `vTaskDelay(2)`，原定 102 到期；101 时被挂起，节点已离开延时链表，102 的到期检查就找不到它。101 时若马上恢复，它直接就绪，不必等到 102。

恢复后接着保存的位置执行，完成原延时调用的返回。之后再次调用延时，会根据新的当前 Tick 重新计算唤醒时刻。挂起不是暂停并保留“剩余倒计时”。

### 4. 恢复就绪就一定立即运行吗？

要看优先级以及是否允许切换。课程中默认任务 24 恢复音乐任务 25，音乐任务可以抢占；若还有持续就绪的 26 级任务，25 就得等。

高优先级任务不必“执行完整个函数”才让出 CPU，调用阻塞函数就能暂时退出竞争。任务函数通常是无限循环。

```c
vTaskResume(xSoundTaskHandle);
bRunning = 1;
```

音乐任务可能在第一句内部就抢占默认任务，第二句要等默认任务重新获得 CPU 才能执行。`bRunning` 只是应用层标志，不是内核任务状态，也不是挂起/恢复的实际操作。

### 5. 重复挂起、重复恢复和提前恢复有什么效果？

- 有效任务被重复挂起，仍然只是挂起状态，不累计次数。本工程实现会先移除状态节点，再插回挂起链表；不会插入多个相同节点。
- 恢复一次即可重新就绪。已不处于显式挂起状态时，再恢复不会重复插入就绪链表。
- 提前恢复不保存“恢复次数”；之后任务挂起，仍需新的恢复操作。
- `vTaskResume()` 不能解除普通 `vTaskDelay()` 阻塞。
- `vTaskSuspend(NULL)` 是挂起自己，后面的代码需等别人恢复后才能继续，无法靠紧随其后的恢复语句自救。

### 6. 高优先级任务阻塞后，会补跑刚才被抢占的任务吗？

不保证。假设 24 级按 A → B → C 轮转，A 被音乐任务抢占；音乐任务随后阻塞，24 级游标从 A 前进一步，选 B。没有“先给 A 补足剩余时间片”的规则。

如果 C 被音乐任务抢占，音乐任务再阻塞，下一次选 A；若中间经过哨兵，就跳过哨兵。

## 三、补充知识点

- **临界区**：保护多步链表修改，防止相关操作插入中间状态；不会把多条赋值变成一条指令。可以嵌套，进入退出必须配对；应保持短小，不在其中调用阻塞函数。
- **请求切换与实际切换**：Cortex-M 上可先请求 PendSV，退出最外层临界区后才允许处理；退出临界区本身不保证发生切换。选中 TCB 后还要恢复现场。
- **任务现场**：任务切出时保存现场；挂起不释放任务栈，局部变量保留，恢复不重跑初始化。第一次运行使用创建时准备的初始现场。
- **事件等待节点**：`xEventListItem` 与状态节点是两个独立节点。显式挂起时，若事件节点已加入等待链表，也会移除。
- **通知等待标志**：挂起时取消“正在等待通知”的标志，不是关闭通知功能。恢复不自动重设等待标志；通知接收函数在需要等待时管理它。被挂起打断的通知等待，恢复后应检查返回值。
- **下一次解除阻塞时间**：挂起延时任务后，`prvResetNextTaskUnblockTime()` 重新检查延时链表，更新最早到期时间，不是重启任务的延时。
